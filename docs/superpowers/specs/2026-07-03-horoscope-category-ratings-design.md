# Per-Category Horoscope Ratings (Health / Career / Marriage / Overall) — Design

**Status:** Approved by user 2026-07-03, ready for implementation planning.

## Context

The `/horoscope` page has two independent horoscope surfaces:

1. **Personalized card** (`app/horoscope/page.tsx`'s `PersonalizedCard`) — grounded in the
   user's own natal chart, generated by an LLM (`backend/src/lib/llm/horoscope.ts`) for
   daily/weekly/monthly/yearly periods, stored in `daily_horoscopes.structured` (jsonb).
2. **12 generic zodiac-sign cards** (the "Moon Sign Horoscope" grid) — not personalized to
   any one user's chart, 100% deterministic (`backend/src/lib/astro-tools/daily-synthesis.ts`
   — real transit-house math + a small set of template hook strings, **zero LLM calls**),
   surfaced via `moonSignPrediction` (daily) and `moonSignPeriodicPrediction` (weekly/
   monthly/yearly, which aggregate sampled daily calls per spec 1.1's "never independent
   narration" rule).

Both currently show a single overall 1–5 star rating + one hook/description/advice block,
identical in shape across all 4 timescales. The ask: break this into four rated categories
(Overall, Health, Career, Marriage), scale the amount of descriptive content up by period
(daily < weekly < monthly, yearly = monthly), and move the personalized card's detail view
into a tappable modal matching the existing moon-sign card pattern (brief on the page, full
detail on tap) rather than always rendering everything inline.

**Out of scope:** the yearly `monthlyBreakdown` (the existing month-by-month modal) stays
overall-only, unchanged — it is not gaining per-category detail per month. Panchang
geolocation is out of scope here (already resolved in a prior session — see
`aroha-backend-architecture` memory).

## Goals

- Every horoscope (personalized and the 12 generic signs), on all 4 timescales, exposes
  four independently-rated categories: `overall`, `health`, `career`, `marriage`.
- `overall`'s **score** is always a server-derived average of the other three (never
  trusted from the LLM for the personalized path, and computed the same way for the
  deterministic path) — but `overall` still gets its own hook/description text, not just a
  number.
- Every category gets its own hook line ("a hook for every text generation").
- Content richness increases with period length: daily is the least detailed, weekly more
  than daily, monthly more than weekly, yearly matches monthly.
- Personalized card: brief summary on the page, full 4-category breakdown in a modal on tap
  (mirrors the existing moon-sign `ForecastDetailModal` pattern).
- No regression: anything currently reading the old singular `hook`/`description`/
  `advice`/`quality`/`score` shape keeps working unchanged.

## Data model

### Shared category shape (both engines)

```ts
export type Category = "overall" | "health" | "career" | "marriage";

export interface CategoryReading {
  hook: string;
  description: string;
  advice: string;
  quality: "good" | "moderate" | "challenging" | "avoid";
  score: number; // 1-5
}
```

### Personalized engine (`db/schema.ts` `StructuredHoroscope`, `horoscope.schemas.ts`)

```ts
export type StructuredHoroscope = {
  // existing fields, KEPT for backward compatibility — mirror categories.overall
  hook: string;
  description: string;
  advice: string;
  quality: "good" | "moderate" | "challenging" | "avoid";
  score: number;
  luckyColor: string;
  luckyNumber: number;
  // NEW
  categories: Record<Category, CategoryReading>;
};
```

`structured` is a jsonb column (`$type<StructuredHoroscope>()`) — this is an additive TS
type change only, **no DB migration needed**.

### Generic engine (`MoonSignPrediction`, `PeriodicMoonSignPrediction` in
`backend/src/lib/swarm/index.ts` re-exports of `daily-synthesis.ts`)

```ts
export interface MoonSignPrediction {
  // ...all existing fields, unchanged...
  categories: Record<Category, CategoryReading>; // NEW
}
export interface PeriodicMoonSignPrediction {
  // ...all existing fields, unchanged...
  categories: Record<Category, CategoryReading>; // NEW
}
```

Existing top-level `hook`/`description`/`advice`/`quality`/`score` fields on both types stay,
mirrored from `categories.overall`.

## Backend: generic (deterministic) engine

Domain-to-house mapping (from the sign, 1-indexed): **Health → 6th, Career → 10th,
Marriage → 7th**. `Overall` = round(average(Health, Career, Marriage)).

Per-domain scoring, per sampled date (daily granularity — periodic predictions already
sample multiple daily calls and aggregate, per the existing `sampleDaily`/`buildPeriodic`
pattern; this repeats per-domain):

1. Compute `domainHouseSignIdx = (signIndex + houseOffset) % 12` (houseOffset = houseNumber − 1).
2. Check which of the already-computed `keyTransits` planets (Sun, Jupiter, Saturn, Rahu,
   Mars, Venus — the existing tracked set) sits in `domainHouseSignIdx`.
3. Natural benefic present (Jupiter, Venus) → **+1** nudge off that day's overall score.
   Natural malefic present (Saturn, Mars, Rahu) → **−1** nudge. Sun is treated as neutral
   here (classification varies by context in classical Jyotish; this is a lightweight
   heuristic, not a full dignity analysis) — same as nothing found → 0 nudge, defer to the
   overall day score as-is.
4. `domainScore = clamp(1, 5, round(overallDayScore + nudge))`.
5. For periodic (weekly/monthly/yearly), average `domainScore` across the sampled dates the
   same way `buildPeriodic` already averages the overall score — reuse, don't reimplement.

Hooks extend the existing `HOOK_TEMPLATES`/`PERIODIC_HOOK_TEMPLATES` pattern: same
tension→resolution template families, parameterized by a domain theme phrase (`"your
health and daily routine"`, `"your career and public standing"`, `"your relationships and
marriage prospects"`) instead of the current house-theme phrase, keeping the same
deterministic-by-seed selection so a given sign/day/domain always renders the same hook
(traceable, cacheable, no drift between requests).

Richness by period (per category):
- **Daily**: hook + score/quality only (no separate description paragraph — matches the
  existing card-view compactness). `advice` is a short template line picked from a small
  per-domain/quality set (same convention as the existing top-level `advice` field in
  `QUALITY_DESC` — e.g. a "challenging" Career reading gets a different templated
  suggestion than a "good" one).
- **Weekly**: hook + 1–2 sentence description (mentions the domain's favorable-day count
  within the week, same style as the existing periodic `description` builder) + the same
  per-domain/quality templated `advice` line.
- **Monthly**: hook + 2–3 sentence description + that domain's best/worst sampled day
  (parallel to the existing overall `bestDay`/`worstDay`, computed per-domain instead) +
  templated `advice`.
- **Yearly**: same richness as monthly (reuses the monthly per-domain description logic
  over the yearly sample points).

## Backend: personalized (LLM) engine

Prompt change in `llm/horoscope.ts`: request four structurally-identical JSON blocks —
`health`, `career`, `marriage`, `overall` — each `{hook, description, advice, quality,
score}`, using the same per-period word budgets already established (daily tightest, weekly
more, monthly most, yearly = monthly), just applied per block instead of once. After
parsing, the server **overwrites** `categories.overall.score` and `.quality` with the
computed average/bucket of health+career+marriage, discarding whatever score the model
assigned to `overall` — only its narrative text (hook/description/advice) is kept. This
guarantees the three-then-derive-overall consistency decided earlier without adding
special-casing inside the prompt itself (all four blocks look identical to the model).

Top-level `hook`/`description`/`advice`/`quality`/`score` on `StructuredHoroscope` become a
straight mirror of `categories.overall`'s fields — existing consumers that only read the
old top-level shape see no change in behavior.

## Frontend

- **`components/ui/BottomSheetModal.tsx`** (new): extracts the shell already duplicated
  between `ForecastDetailModal` and `MonthlyBreakdownModal` (backdrop, spring-in sheet,
  sticky header with a content slot, scrollable body, close button, bottom safe-area
  padding). Both existing modals are refactored onto it; no visual change for either.
- **`components/horoscope/CategoryRatingRow.tsx`** (new): one category's icon + label +
  5-star row + hook (+ expandable description/advice), reused by both modals below. Icons:
  Sparkles (Overall), HeartPulse (Health), Briefcase (Career), Heart (Marriage) — all
  already available via `lucide-react`, already used elsewhere in this codebase.
- **Personalized card** (`PersonalizedCard` in `app/horoscope/page.tsx`): page view stays
  brief — Overall stars + Overall hook + quality badge + lucky-color/number tiles, as
  today, reading from `categories.overall` instead of the top-level fields. The whole card
  becomes tappable (matching the 12-sign grid tiles' existing tap-to-open pattern) and
  opens a new **`PersonalizedDetailModal`** (built on `BottomSheetModal`) listing all four
  `CategoryRatingRow`s, scrollable. Yearly's existing "view month-by-month" entry point
  remains reachable from inside this new modal, unchanged.
- **`ForecastDetailModal`** (12-sign modal): rebuilt on `BottomSheetModal`; gains the same
  four `CategoryRatingRow`s. The grid tiles on the page are unchanged (space-constrained —
  single overall star row stays there); the 4-category breakdown lives in the modal only.
- **Types**: `components/horoscope/types.ts` and `lib/api.ts` gain `Category`,
  `CategoryReading`, and the `categories` field on the relevant interfaces.
- **i18n**: new keys for the four category labels, the personalized card's "view full
  reading" affordance, and any new modal chrome strings — added across all 7 languages
  (en, hi, bn, mr, te, ta, gu), per this project's i18n rule.

## Non-goals / explicitly deferred

- No change to panchang, chat personas, or the yearly monthly-breakdown modal's content
  shape.
- No new LLM calls added to the generic 12-sign engine — it stays 100% deterministic.
- No change to the underlying Vedic house-mapping conventions beyond the three new
  domain-house associations (6th/10th/7th) documented above.
